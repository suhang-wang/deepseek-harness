# Enterprise product requirements

English | [中文](product-requirements.zh.md)

## Summary

Employees sign in with their company WeCom identity and use approved DeepSeek models without handling corporate API keys. Administrators synchronize the authorized organization, configure access and output quotas, and inspect usage. This is a design reference under the [design status](README.md).

<a id="scope"></a>
## Users and scope

| Role | Permissions |
| --- | --- |
| Employee | Sign in/out, view only their own identity, department paths, cost department, effective models and quota in the desktop, and run local Harness tasks. |
| Enterprise administrator | Use the admin website to manage authorized employees, qualified model policies, quotas, sessions, synchronization, usage reports, and audit records. |
| Enterprise owner | Perform administrator actions and additionally grant or revoke administrators and owners and rotate the server-side DeepSeek API key. |

The first owner signs in with WeCom and enters a short-lived, one-use initialization code bound to that employee and generated by an explicit server operation. The code is available only before initialization and cannot be reused when all owners are later lost; subsequent grants come from an owner or a separate audited operator recovery action. Non-administrators cannot enter the admin website, and department leadership does not automatically grant administration. This iteration uses the WeCom browser session without a passkey step-up. The initial platform is macOS arm64; other desktop targets require their own release qualification.

Included: single-company login, authorized department trees and membership, employee lifecycle, managed DeepSeek Messages streaming with local tools and reasoning, supported image/file paths, model settings, output quotas, usage estimates, audit, enterprise updates, and optional employee-owned model providers. The company gateway and employee catalog publish only qualified provider/model combinations. The first OpenAI-compatible candidate is the Beijing DashScope `qwen3.8-omni-flash` endpoint; a saved provider draft alone is not a callable company model. Excluded: SaaS tenancy, unqualified centrally managed vendor inference, HR writeback, approval workflows, knowledge bases, centralized conversation storage, and unattended remote control of employee machines.

<a id="requirements"></a>
## Requirements

All requirements below are required for the first release. The [test reference](test-cases.md) maps each identifier to concrete acceptance cases; implementation rules belong to the [technical design](technical-design.md).

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| PR-01 | WeCom login | Only authorized, enabled employees receive a desktop session; cancellation, expiry, and retry have clear outcomes. |
| PR-02 | Organization synchronization | Import the authorized department tree and employees; show sync time, scope, counts, failures, and manual retry. |
| PR-03 | Membership and cost department | Retain multiple memberships and one validated cost department per employee; unresolved attribution blocks inference. |
| PR-04 | Model policy | Manage only qualified company models and company, department, and employee restrictions; preview effective models, defaults, and reasons. |
| PR-05 | Enterprise inference gateway | DeepSeek Messages retain streaming, tool execution cycles, reasoning replay, and supported images; a separately qualified OpenAI-compatible route supports its verified text and tool-call capabilities. |
| PR-06 | Quota and usage | Reserve and settle output-token quotas without concurrent overspend; distinguish confirmed, reserved, and uncertain usage. |
| PR-07 | Access revocation | Logout, session revocation, disablement, and confirmed removal stop future gateway requests. |
| PR-08 | Data and credential protection | Corporate keys remain encrypted server-side and never appear in admin reads; employee file access is isolated; optional official uploads are disabled. |
| PR-09 | Administration and audit | Grant the first owner only after bound one-use initialization; reject employee admin access, enforce owner-only grants/key rotation, and audit privileged changes. |
| PR-10 | Desktop distribution | Install an identifiable enterprise client with independent data directories and the company update channel. |
| PR-11 | Upstream compatibility | Pin a qualified upstream/plugin/API combination and verify existing session data before upgrades. |
| PR-12 | Operations and failure recovery | Expose actionable health, stale-directory, upstream, and uncertain-ledger alerts with tested recovery. |

<a id="flows"></a>
## Product flows and pages

Employee onboarding: open the enterprise app, scan its embedded WeCom login QR code, confirm on the phone, and enter the workspace automatically after authorization. The system browser remains an alternative when QR login is unavailable. An employee who has not logged in can already appear in the synchronized admin directory. An inactive employee, unresolved cost department, or empty model policy receives a reason and an administrator contact path.

Normal use: the model picker shows qualified company models and any employee-owned providers, with their source identified. Every company-model call, including task titles, compaction, and subagent work, consumes the relevant enterprise quota. Employee-owned providers use personal credentials and their own billing; they do not use the enterprise gateway or enterprise quota. Missing or revoked enterprise access leaves local history readable while new corporate inference is unavailable.

| Page | Required information and actions |
| --- | --- |
| Desktop sign-in/account | Own company and employee identity, department paths, cost department, session state, retry/cancel/signout, and actionable errors. |
| Desktop model settings | Original model-provider add/edit controls for employee-owned models; read-only company provider group listing the current employee-visible model names. Corporate credentials and endpoint remain managed. |
| Organization and employees | Tree, search, multiple memberships, cost department, sync state, and disable/revoke actions. |
| Administrator access and provider | Owners manage administrator grants and provider API keys; the keys are never readable after submission, and the page shows configuration/version state. |
| Policies and quotas | Company/department/employee scopes, effective preview, revision conflicts, and monthly limits. |
| Usage and audit | Employee and cost-department aggregation, token classes, estimated cost, uncertain records, and privileged operations. |
| System status | Directory freshness, gateway health, upstream access, compatibility requirements, and failed background jobs. |

<a id="policy-experience"></a>
## Policy experience

Explicit restrictions combine conservatively across company, department memberships, and employee settings. The interface explains which restrictions apply and never silently substitutes a different model. Cost allocation uses one server-owned department; displaying several memberships does not charge several peer departments for one request.

Quota is measured in generated output tokens, including reasoning where the qualified upstream protocol counts it. Administrators configure finite monthly company, employee, and cost-department limits. Input/cache token statistics and versioned prices support estimated monetary reports; upstream bills remain the reconciliation authority. Unknown usage is visible and cannot appear as a confirmed zero charge.

The model list cannot enable an unqualified DeepSeek model; the first approved model is `deepseek-flash`. A key replacement affects newly admitted calls; already admitted calls and owned Files operations retain the credential version they require until safe cleanup. If no key is configured, the admin website remains available while model calls clearly report unavailability.

The administrator's Models & Policy page uses provider cards with readable model lists and inline editors, following the desktop Models page's structure. An owner may add an OpenAI-compatible draft with a public HTTPS base URL, model IDs and a write-only API key; the saved card lists those model IDs. Employee use remains pending until the exact endpoint, model list, key revision, output bound, and usage semantics pass qualification and the owner publishes the resulting record. The page separates provider configuration and owner-only key replacement from company, department, and employee policy. Common policy fields use labeled controls and an effective-value preview; advanced JSON editing remains available without discarding fields outside the form. Scope changes and revision conflicts must preserve an unsaved draft or require an explicit discard decision.

The enterprise distribution routes company-model calls through the gateway. The original Models page permits employee-owned providers with local credentials; the company provider appears as a read-only group listing each currently available company model by name, without edit or local key controls. Model policy and quota details stay in the administration workspace. The Enterprise Account page displays only company and employee identity and organization information. It shows the visible root company's name and the employee's WeCom name when available, with stable IDs as secondary identifiers; missing names fall back to IDs. Personal-provider traffic and charges are outside the enterprise gateway, policy, quota, revocation, and audit boundary; users must choose that route knowingly. A device or network policy is needed to restrict all machine traffic.

<a id="acceptance"></a>
## Acceptance objectives

The following values are proposed acceptance targets, not measured results. The pilot baseline is 1,000 employees, 100 departments, and 40 simultaneous model streams, with at most two active calls per employee.

| Area | Target and measurement condition |
| --- | --- |
| Revocation | After the backend revocation transaction commits, new admissions fail; active streams are aborted within five seconds. |
| WeCom changes | Poll every 15 minutes; distinguish detection delay from backend enforcement. A failed sync raises an alert and does not count as successful lifecycle processing. |
| Directory availability | A first complete authorized snapshot is required before access; a snapshot older than 60 minutes blocks new login and inference. |
| Gateway overhead | At the pilot baseline, p95 admission overhead is at most 200 ms and p95 relay delay is at most 50 ms; exclude upstream generation and human login time. |
| Correctness | All P0 cases pass, no unresolved critical/high security defects, no duplicate settlement, and no cross-employee file disclosure. |
| Qualification | Real WeCom, real DeepSeek Messages/Files, signed macOS installation, update, and migration evidence are required before company-wide release. |
